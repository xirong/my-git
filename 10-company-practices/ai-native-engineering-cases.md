# 两个 AI Agent 工程案例：把公开报告转成团队决策

[English](10-company-practices_en/ai-native-engineering-cases_en.md) | 中文

公开案例可以帮助团队提出更好的问题，不能替代团队自己的权限、Git、CI 和审查规则。本篇只讨论两个第一手报告：Ramp 对内部后台编码平台 Inspect 的介绍，以及 Cursor 对长期并行 Agent 实验的说明。两篇原文的目的、环境和证据强度不同，因此需要分别阅读。

本文把每一节分成“作者报告”“团队可推导的做法”和“没有被证实的事”。报告中的数字均保留发表时间与自报属性，不能视作独立质量测量，也不能推导为其他团队可复制的收益。

## 阅读前先区分两类证据

| --- | --- | --- | --- |

两篇都是作者方的一手叙述。它们提供了设计选择和自报观察，却没有给出独立复现实验、完整成本、缺陷率或普通团队迁移后的结果。

## 案例一：Ramp Inspect 的重点是让结果带着验证上下文回来

### 作者报告

Ramp 介绍了其内部后台编码 Agent Inspect：后端任务可用测试、遥测和 feature flag，前端任务可做视觉核对并给出截图和预览。其公开架构将每次 session 放入隔离 sandbox，并提到预建镜像、文件系统快照、仓库同步和用用户 GitHub token 创建 PR。

作者自报在发表时，约 30% 合入其前后端仓库的 PR 由 Inspect 编写，达到这个比例花了数月。这是 Ramp 的内部使用报告，不是对缺陷率、审查质量、成本或外部可复制性的独立测量；原文也没有公开具体仓库的权限、网络或生产数据边界。

### 团队可推导的做法

1. 把“可以做什么”与“可以证明什么”一起写进任务契约。测试、遥测、feature flag、截图等工具要有最小权限、输入来源、运行环境和输出位置，结果才可被审查。
2. 每个任务使用可归属的隔离目录、分支或执行环境。隔离降低编辑互相覆盖的机会，却不会自动决定哪些路径能改，也不会替人确认业务含义。
3. 把 PR、candidate SHA、测试输出和 session 记录关联。工具输出若没有命令、时间、环境和 SHA，只能作为线索。
4. 并发 session 增加时，审查、CI 和集成能力也要随之规划。提交产出比审查容量快时，应收紧任务范围或限制并发，不能让待审 PR 无限堆积。

这些做法和[后台 Agent 任务回收流程](../05-ai-native-development/background-agent-workflow.md)的任务契约、候选 SHA 与现场保留相连；[AI 生成变更的 CI](../05-ai-native-development/ci-for-ai-generated-changes.md)说明怎样继续把检查结果绑定到候选版本。

### 没有被证实的事

- 原文没有提供 Inspect 任务的独立成功率、人工审查耗时、返工比例或安全事件数据。
- 约 30% 的数字没有说明所有 PR 的复杂度、团队基线和统计口径，不能用来设定本团队 KPI。
- 镜像快照和远程 sandbox 是否适合某个代码库，取决于构建时长、依赖许可、网络隔离、数据分类和预算，需要本地试点验证。

## 案例二：Cursor 的重点是并行之前先定义职责和汇合点

### 作者报告

Cursor Research 记录了长期自主编码实验：同级 Agent 通过共享文件和锁领任务时，作者报告约二十个 Agent 的有效吞吐会降到两三个。后续将职责拆为持续产出任务的规划者、专注任务的执行者，以及每轮决定是否继续的判定者。

作者还报告了接近一周、超过一百万行和一千文件的浏览器项目，以及持续三周以上、`+266K/-193K` 改动的 Solid 到 React 迁移。原文说迁移仍需仔细审查，只通过了其 CI 和早期检查。以上观察均为 Cursor 作者在 2026-01-14 的自报，不表示质量、可维护性或可复制收益。

### 团队可推导的做法

1. 在扩大并发前切分边界。按目录、组件、服务或清晰的行为切任务，并给每项任务一个负责人、base SHA、允许路径和验证方式。共享状态文件和全局锁很容易成为新的串行点。
2. 规划、实现和接受可以是不同职责。规划者给出可执行边界，执行者交 candidate，判定者检查是否继续；其中的判定者仍不能代替具备业务与合并权限的人类接收人。
3. 汇合点必须有容量。每个 candidate 都会占用 CI、冲突处理和审查注意力；并发数应受这些容量、任务独立性和风险等级约束。
4. 每轮从已确认的集成状态重新开始。这样可以发现 base 变化、重复运行和同路径冲突，并把旧结果作为显式输入，而非悄悄混入下一轮。

这与[多 Agent 分支策略](../05-ai-native-development/multi-agent-branch-strategy.md)的隔离原则、[一次 Agent 变更，如何从意图走到验收](../05-ai-native-development/ai-change-control-loop.md)的候选证据和[AI Agent 事故恢复](../06-troubleshooting/ai-agent-incident-recovery.md)的失败现场保留构成一条链。

### 没有被证实的事

- 原文没有给出锁方案和职责分离方案在相同代码库、相同任务集上的受控比较数据。
- 数百个 Agent 向同一分支推送的报告不等于普通团队应共享一个分支。没有明确隔离和集成规则时，这会放大冲突与错误归属风险。
- 文章中的模型比较与主张不构成本手册的模型选择建议；团队应按自己的任务、权限、延迟、成本、测试和审查结果评估。

## 用两个案例反推自己的试点

这两个案例可借鉴的前提不同：Ramp 更强调单个后台 session 的运行环境与验证信息；Cursor 更强调大量任务的分工和协调。共同的最低条件是任务能被明确切分、候选能定位到 SHA、验证有可复查输出、人工审查和集成有明确责任。

建议从一条低风险、可回滚的路径试点：

1. 选一个有稳定测试且不涉及生产写入、密钥或高敏数据的任务。
2. 用[后台 Agent 任务回收流程](../05-ai-native-development/background-agent-workflow.md)记录任务 ID、base、允许路径、权限、候选、证据和接收决定。
3. 限制并发到团队能审查并集成的数量，记录 base 变化、冲突、返工、验证失败和人工处理时间。
4. 在多个任务后回看这些本地记录，再决定是否增加工具权限、扩展路径范围或提高并发。

公开报告提供的是假设和设计线索。本团队是否收益，必须由自身仓库、数据分类、CI、审查容量和交付结果验证。
